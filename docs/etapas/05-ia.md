# Etapa 5 — risco com modelo de IA treinado

Modelo: regressão logística binária, treinada de fato por gradient descent sobre 2.400 exemplos sintéticos e avaliada em outros 600, seed=42. Features versionadas: temperatura relativa a 25°C, déficit de bateria e criticidade codificada. Pesos e hash do dataset estão em `models/iot-risk.json`; a versão inclui fingerprint dos pesos, features e dados. Não é uma soma manual de regras apresentada como aprendizado.

Avaliação observada: accuracy 0,936667; F1 0,946328; ROC AUC 0,983995. Esses números medem o problema sintético criado no gerador e **não comprovam desempenho em equipamento real nem fraude de pagamentos**. O score é uma probabilidade estimada para o alvo sintético; não há validação/calibração para uso operacional real. Limiares de apresentação: high >=0,8; medium >=0,4; low abaixo disso.

## Treinar e verificar

```bash
python3 -m ai.train
python3 -m unittest discover -s tests -v
./setup.sh
```

O modelo é artefato JSON legível, sem pickle ou serviço externo. Setup usa o modelo versionado e não o retreina silenciosamente. Treino não depende de API key, GPU ou cobrança de IA externa. [Saída de treino](../../evidence/steps/05/training.txt) e [testes locais](../../evidence/steps/05/unit-tests.txt).

## Enriquecer o stream

O worker `iot-scorer` lê `iot.enriched` em Avro, aplica o modelo e publica chave Avro + valor Avro no tópico `iot.risk.scored`. Campos incluem reading_id, device_id, risk_score, risk_level, model_version, observed_at e site_id. Propaga tombstones. Saída e offset de entrada são confirmados na mesma transação Kafka; consumidores usam read_committed. Isso não transforma os efeitos externos do consumidor em exactly-once.

O teste integrado consome scores reais, exige versão do modelo e probabilidades válidas, compara sensor quente (>0,8) com sensor normal (<0,4), verifica remoção da leitura excluída e passagem da leitura válida 101 após os registros defeituosos. Entradas inválidas para o modelo vão para a DLQ; falhas de infraestrutura não são descartadas. Modelo ou formato de features incompatível precisam de nova versão e validação antes do deploy.

`iot-risk.json` e `iot-validation.txt` são publicados no artefato `pipeline-evidence` do workflow da etapa 5. Não são substituídos por previsões offline para alegar streaming. O teardown remove também o scorer. A implantação do worker no Cloud e o Tableflow permanecem fora da execução local comprovada.
